# PostgreSQL vs MySQL vs SQLite

A deployment- and architecture-first comparison of three mature relational databases, focused on where the engine runs, how concurrency and durability work, and which operational boundary fits the application.

**Verified:** 2026-09-06

## Compared modules

- [PostgreSQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/postgresql/entry) (`database/postgresql`) — `deep-dive` — Open-source relational database known for standards-oriented SQL, transactions, extensibility, advanced data types, indexing, and reliable server workloads.
- [MySQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/mysql/entry) (`database/mysql`) — `deep-dive` — Widely used relational database management system implementing SQL for transactional and web workloads with a large ecosystem of tools and integrations.
- [SQLite](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/sqlite/entry) (`database/sqlite`) — `deep-dive` — Embedded relational database engine that stores a complete database in ordinary files and requires no separate database server process.

## Comparison

| Dimension | [PostgreSQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/postgresql/entry) | [MySQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/mysql/entry) | [SQLite](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/sqlite/entry) |
| --- | --- | --- | --- |
| **Engine boundary** | Separate client/server database process architecture. Applications connect to a PostgreSQL server instance that owns shared database state, transactions, authentication, and storage operations. | Separate client/server SQL server. The server layer handles sessions, SQL, privileges, binary logging, and replication coordination while storage engines such as InnoDB implement transactional row and index storage. | Embedded database library linked into the application process. SQL execution and file I/O happen in-process; there is no separate database daemon or native remote database protocol. |
| **Primary storage model** | Heap-organized table storage with separate index access methods. Row versions participate in PostgreSQL MVCC, while indexes reference table tuples and require maintenance as table state changes. | InnoDB normally organizes table rows by the clustered primary-key B-tree; secondary-index entries carry the primary-key identity, making primary-key width and insertion locality important physical design choices. | Ordinary rowid tables use a table B-tree keyed by integer rowid; secondary indexes identify rows through rowid. WITHOUT ROWID tables instead use the declared primary key as the table B-tree key. |
| **Concurrency model** | MVCC allows concurrent readers and writers while row/table locks and serialization rules coordinate conflicting changes. Many write transactions can progress concurrently when they do not conflict on the same resources. | InnoDB combines MVCC with record, gap, and next-key locking. Many writers can progress concurrently on different data, while lock ordering, range access, and isolation semantics can produce waits or deadlocks. | Multiple readers can coexist, but only one write transaction can modify a database file at a time. WAL mode allows readers and a writer to overlap, but it does not create multiple simultaneous writers. |
| **Durability and journal model** | Write-ahead logging records changes before data pages need to reach final storage; checkpoints and crash recovery reconcile WAL with relation files. WAL also underpins physical replication and PITR workflows. | InnoDB redo supports storage-engine crash recovery and undo supports rollback/MVCC history. The server binary log is a separate logical history used for replication and point-in-time recovery workflows. | Uses either rollback-journal transactions or a write-ahead log. The pager coordinates atomic commit and locking; WAL checkpoints copy committed frames back into the main database file. |
| **Remote client access** | Designed for networked clients connecting to a database server. Authentication, TLS, roles, connection limits, pooling, and server exposure are explicit operational concerns. | Designed for networked clients connecting to a database server. Accounts, authentication plugins, TLS, connection handling, privileges, and server routing are part of the normal deployment boundary. | Has no built-in client/server listener. The application using SQLite should normally be on the same machine as the database file; remote clients should talk to an application service rather than the live file. |
| **Replication and HA primitives** | Provides physical streaming and logical replication primitives. Production automatic failover, routing, fencing, multi-region policy, and topology management are completed by external tooling or managed services. | Provides binary-log replication and Group Replication primitives; the wider InnoDB Cluster ecosystem adds management and routing components. Application HA still depends on tested topology and failover behavior. | Core SQLite does not provide built-in multi-node replication, consensus, automatic failover, or remote topology management. Replication or sync must be added at another layer when required. |
| **Backup and point-in-time recovery** | Supports logical and physical backup approaches plus WAL archiving and replay for point-in-time recovery. Recovery design depends on retaining a valid base backup and the required WAL history. | Supports logical/physical backup approaches and point-in-time recovery by restoring a known-good backup and replaying required binary-log history. Retention and restore verification are part of the design. | Provides safe online backup and file-copy/rebuild mechanisms such as the backup API and VACUUM INTO. Core WAL is not a long-term PITR archive; historical recovery points require an explicit application or snapshot strategy. |
| **Main operational responsibilities** | Server capacity, connections, planner statistics, vacuum/autovacuum, WAL, checkpoints, locks, replication, backup/restore, upgrades, security policy, and incident diagnosis all require ongoing operational ownership. | Server capacity, connections, InnoDB buffer/redo behavior, optimizer statistics, locks, binary logs, replication, backup/restore, upgrades, privileges, and HA routing require ongoing operational ownership. | No server fleet is required, but the application owns migrations, transaction duration, busy handling, journal/WAL settings, checkpoints, backups, live-file handling, filesystem assumptions, and corruption recovery. |
| **Extensibility model** | Rich server extensibility includes types, functions, operators, extensions, index/access methods, procedural languages, foreign data wrappers, and a broad extension ecosystem. | Extensibility includes plugins/components, functions, authentication integrations, and a pluggable storage-engine architecture, with capabilities and availability depending on edition and deployment environment. | Extensible in-process through application-defined functions and collations, virtual tables, loadable extensions when enabled, and bundled capabilities such as FTS5 and JSON support in appropriate builds. |
| **Primary-key storage consequences** | A primary-key constraint normally creates a unique index but does not make the table itself a permanently primary-key-clustered structure. Heap layout and index maintenance are separate concerns. | InnoDB uses the primary key as the clustered table key. Wide or random keys can increase secondary-index size, page churn, and storage/write amplification because secondary indexes include primary-key identity. | INTEGER PRIMARY KEY aliases rowid in ordinary tables, while other primary keys are not automatically the rowid storage key. WITHOUT ROWID changes this by storing the table according to its declared primary key. |
| **Strong fit** | Shared networked application data where concurrent transactions, advanced SQL, extensibility, strong operational tooling, and PostgreSQL-specific capabilities justify a dedicated database server boundary. | Shared networked application data where the MySQL protocol/ecosystem, InnoDB operational model, replication tooling, managed-service compatibility, or existing organizational expertise are important constraints. | Application-owned local state, mobile/desktop/embedded storage, single-file application data, offline-first caches, or server-local workloads whose write concurrency fits the one-writer-per-database-file model. |
| **Reconsider when** | The application only needs simple local embedded persistence and introducing a separately operated database service would add more operational surface than the workload warrants. | The application only needs simple local embedded persistence and introducing a separately operated database service would add more operational surface than the workload warrants. | Many machines must directly share one live database file, many concurrent writers cannot queue, or the system requires built-in server-side replication/failover and centralized remote database administration. |
| **Core licensing boundary** | PostgreSQL is distributed under the permissive PostgreSQL License. | MySQL Community Edition is distributed under GPL-2.0, while Oracle also offers commercial licensing and products around MySQL. | SQLite's deliverable code and documentation are dedicated to the public domain. |

## Decision guide

- **When:** The data belongs to one application or device and should remain usable without deploying or reaching a separate database service. **Consider:** [SQLite](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/sqlite/entry). SQLite removes the server/network boundary and is designed for local application-owned storage, provided the workload fits its write-concurrency and filesystem model.
- **When:** Many remote application instances need to share one authoritative relational database and concurrent writes are a normal part of the workload. **Consider:** [PostgreSQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/postgresql/entry), [MySQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/mysql/entry). A client/server engine provides a central transaction coordinator, remote protocol, account model, and substantially more concurrent write capacity than one shared SQLite file.
- **When:** The application depends on PostgreSQL-specific SQL behavior, extensions, access methods, or an existing PostgreSQL operational platform. **Consider:** [PostgreSQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/postgresql/entry). Product-specific semantics and operational expertise are stronger selection criteria than generic claims about one relational database being universally faster or more scalable.
- **When:** The application depends on the MySQL protocol/ecosystem, InnoDB behavior, MySQL-compatible managed services, or an existing MySQL operational platform. **Consider:** [MySQL](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/mysql/entry). Compatibility requirements, replication/HA tooling, and existing expertise can make MySQL the correct boundary even when another engine offers overlapping SQL features.
- **When:** A remote service architecture is still desired, but the database itself can remain server-local and writes can be serialized efficiently by the application service. **Consider:** [SQLite](https://github.com/BLCCoreStudio/OpenDevIndex/tree/database/sqlite/entry). SQLite can sit behind an application-specific network API while remaining local to that server; remote clients do not need direct access to the database file.
