# Containers vs Docker vs containerd

An abstraction- and runtime-boundary comparison of Linux containers, Docker, and containerd, clarifying the difference between the underlying isolation model, developer-facing container workflows, and node-level container lifecycle management.

**Verified:** 2026-09-06

## Compared modules

- [Containers](https://github.com/BLCCoreStudio/OpenDevIndex/tree/concept/containers/entry) (`concept/containers`) — `deep-dive` — Operating-system-level isolation model that packages applications with dependencies while sharing a host kernel and using standardized image and runtime formats.
- [Docker](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/docker/entry) (`tool/docker`) — `deep-dive` — Container development platform centered on portable images and isolated application processes, widely used for packaging and deployment workflows.
- [containerd](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/containerd/entry) (`tool/containerd`) — `deep-dive` — Industry-standard container runtime focused on managing the complete container lifecycle, including image transfer, storage, execution, supervision, and low-level runtime integration.

## Comparison

| Dimension | [Containers](https://github.com/BLCCoreStudio/OpenDevIndex/tree/concept/containers/entry) | [Docker](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/docker/entry) | [containerd](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/containerd/entry) |
| --- | --- | --- | --- |
| **Abstraction level** | A systems concept and execution model built from operating-system primitives such as namespaces, cgroups, capabilities, filesystems, and process isolation, with OCI standards defining portable image and runtime boundaries. | A developer-facing container platform and toolchain that packages image build, distribution, container creation, networking, volumes, CLI workflows, and daemon APIs into an integrated experience. | A long-running container runtime daemon and API layer that manages content, images, snapshots, containers, tasks, shims, and lower-level runtime execution on a node. |
| **Primary responsibility** | Explain and provide the isolated process model itself, including what is and is not isolated, how resources are constrained, and how image/runtime standards map onto kernel behavior. | Turn container primitives into practical build, run, inspect, publish, networking, storage, and local-development workflows with a cohesive CLI and platform UX. | Provide reliable node-local lifecycle services for pulling and unpacking images, preparing root filesystems, starting tasks, supervising runtime processes, and exposing runtime APIs to higher layers. |
| **Process isolation** | Namespaces, cgroups, capabilities, seccomp, mount behavior, and other kernel mechanisms form the real isolation and resource-control boundary. Containers are still host processes rather than virtual machines. | Configures and invokes underlying runtime mechanisms to create isolated container processes, while exposing higher-level flags and defaults rather than implementing kernel isolation primitives itself. | Coordinates task creation through OCI-compatible lower-level runtimes and shims, relying on the host kernel and runtime implementation for the actual namespace, cgroup, capability, and seccomp isolation. |
| **Image build responsibility** | OCI image concepts define layers, manifests, configuration, and root filesystem materialization, but the container concept itself is not an image build engine. | Image construction is a major workflow through Dockerfile and BuildKit-based build tooling, cache management, multi-stage builds, build contexts, and registry publication. | Consumes and manages image/content artifacts but is not primarily a developer image-authoring system. Image build normally happens in Docker, BuildKit, CI tooling, or another builder before containerd consumes the result. |
| **Image and content storage** | The portable model is content-addressed OCI image data and unpacked root filesystem layers, while concrete local content stores are implementation choices made by tools and runtimes. | Maintains local image and build state behind Docker workflows and exposes familiar image commands, tags, pulls, pushes, pruning, and build cache behavior. | Has explicit content and image metadata stores keyed by digests and references, plus snapshotter-managed unpacked filesystem state used to prepare runnable root filesystems. |
| **Container versus running process object** | Conceptually separates image/root filesystem, container configuration, and the running process even though user-facing tools may hide those layers behind one command. | Presents containers as high-level lifecycle objects through create, start, run, stop, exec, inspect, logs, and remove workflows, abstracting several lower-level runtime objects. | Distinguishes container metadata from tasks. A container describes configuration and resources, while a task represents the live runtime process managed through a shim and lower-level runtime. |
| **Daemon and API boundary** | The container abstraction does not require one universal daemon API. Different engines and orchestrators can implement the model through different control planes while sharing OCI contracts. | Docker Engine exposes a higher-level daemon API and CLI-oriented workflow surface that covers build, image, container, network, volume, and related platform operations. | Exposes a runtime-focused gRPC API used by clients and higher-level systems, with namespaces and plugins organizing node-local resources and services. |
| **Lower-level runtime boundary** | OCI runtime specifications define the contract for creating and running a container bundle, while implementations such as runc translate that contract into kernel process setup. | Normally delegates runtime execution through lower layers rather than directly implementing every OCI runtime primitive in the Docker CLI or high-level daemon workflow. | Manages task lifecycle and delegates low-level process creation to OCI runtime implementations through runtime v2 shims, keeping task supervision separate from the containerd daemon process. |
| **Networking responsibility** | Network namespaces, virtual interfaces, routing, bridges, firewall or policy rules, and higher-level network plugins determine how isolated processes communicate. | Provides user-facing container networking with bridge and other network drivers, port publishing, DNS/service-name behavior, and Docker-managed network objects. | Core containerd is not a Docker-style end-user network UX. In orchestrated environments networking is commonly coordinated through CRI and CNI or another higher-level integration around runtime task creation. |
| **Persistent storage responsibility** | Writable container layers are usually ephemeral relative to workload lifecycle, while durable application data belongs on explicitly managed mounts, volumes, or external storage systems. | Exposes volumes, bind mounts, tmpfs options, copy-on-write image layers, and storage-driver behavior through developer and operator workflows. | Uses snapshotters to materialize and manage container root filesystem snapshots; durable application data and orchestration-level volume semantics are generally owned by higher layers. |
| **Kubernetes boundary** | Kubernetes schedules and reconciles containerized workloads but depends on a concrete runtime implementation and networking/storage integrations to turn pod specifications into running isolated processes. | Docker is widely used to build and test images used by Kubernetes, but modern Kubernetes nodes do not require the Docker Engine as their Container Runtime Interface implementation. | Commonly serves Kubernetes nodes through its CRI plugin, translating pod sandbox and container lifecycle requests into image, snapshot, task, shim, and runtime operations. |
| **Developer workflow** | Supplies the mental model needed to reason about images, namespaces, cgroups, root filesystems, isolation, and lifecycle regardless of which concrete tool is used. | Optimized for direct developer interaction through commands such as build, run, compose-oriented workflows, logs, exec, inspect, image management, networking, and local iteration. | Usually sits below higher-level tooling. Direct clients such as ctr or nerdctl may be used for diagnostics or specialized workflows, but containerd itself is primarily infrastructure rather than a complete developer UX. |
| **Security boundary** | Security depends on the shared-kernel threat model, namespace boundaries, Linux capabilities, seccomp, LSM policy, user namespaces, filesystem mounts, image provenance, and host hardening. | Security additionally includes daemon/socket authority, build-context and Dockerfile trust, registry provenance, privileged flags, bind mounts, secrets handling, and Desktop or Engine configuration. | Security additionally includes daemon socket access, plugin and runtime configuration, content provenance, shim/runtime binaries, snapshotter behavior, CRI privileges, and node-level filesystem/socket permissions. |
| **Typical failure boundary** | Failures arise from kernel limits, cgroup pressure, namespace or mount assumptions, filesystem exhaustion, network policy, capability restrictions, image incompatibility, or misunderstanding shared-host behavior. | Failures commonly involve build cache or context issues, daemon availability, image pulls, storage pressure, network and port configuration, volume ownership, registry access, or container configuration. | Failures commonly involve content pulls, unpacking, snapshotters, task and shim lifecycle, runtime binaries, CRI integration, namespace selection, disk pressure, or node-level daemon/plugin health. |
| **Upgrade and compatibility boundary** | Stable OCI contracts and kernel interfaces reduce coupling, but application compatibility can still depend on architecture, kernel features, cgroup versions, security policy, and image assumptions. | Upgrades can affect Engine, CLI, BuildKit, Compose integrations, storage/network behavior, API versions, Desktop components, and defaults that shape developer workflows. | Upgrades can affect daemon plugins, CRI behavior, snapshotters, runtime v2 shims, configuration versions, Kubernetes compatibility, and lower-runtime integration on production nodes. |
| **Choose or learn when** | You need to understand the fundamental execution, isolation, filesystem, resource-control, security, and OCI model that remains valid across Docker, containerd, Kubernetes, and other container systems. | You need a cohesive developer and operator toolchain for building images, running and debugging containers, publishing artifacts, managing local networks and volumes, or providing an approachable container UX. | You need a production-oriented node runtime daemon, CRI-compatible Kubernetes runtime, embeddable container lifecycle API, explicit snapshotter/content management, or a stable layer beneath higher-level platforms. |
| **Common composition** | Defines the process and image model that concrete tools implement and compose around. | Can use containerd and OCI runtimes internally while presenting a broader developer-facing Engine and CLI experience above them. | Can sit beneath Docker or Kubernetes, managing images and running tasks while higher layers own build UX, application orchestration, policy, and user-facing workflows. |
| **Do not assume** | Do not treat containers as a product that can replace Docker or containerd. Containers are the systems model and standards boundary those tools implement or expose. | Do not assume Docker and containerd are interchangeable just because both run containers. Docker provides a broader developer platform and higher-level workflow surface around lower runtime services. | Do not assume containerd is a drop-in replacement for Docker's full build, Compose, network, volume, and developer experience. Its core responsibility is narrower node-level runtime lifecycle management. |

## Decision guide

- **When:** The goal is to understand why container isolation works, what shares the host kernel, and how namespaces, cgroups, capabilities, filesystems, and OCI contracts fit together. **Consider:** [Containers](https://github.com/BLCCoreStudio/OpenDevIndex/tree/concept/containers/entry). The containers deep dive owns the technology-independent systems model that remains useful even when the concrete engine or orchestrator changes.
- **When:** Developers need one approachable workflow for building images, running local containers, inspecting logs, publishing images, and managing common networks and volumes. **Consider:** [Docker](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/docker/entry). Docker packages those developer-facing workflows behind a cohesive CLI and Engine rather than exposing only the lower runtime lifecycle primitives.
- **When:** A Kubernetes node or platform component needs a stable daemon that manages image content, snapshots, tasks, shims, and OCI runtime execution through CRI or another API. **Consider:** [containerd](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/containerd/entry). containerd is designed around that node-local lifecycle and runtime service boundary and is commonly used underneath Kubernetes.
- **When:** A team is replacing Docker with containerd because Docker uses containerd internally. **Consider:** [Docker](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/docker/entry), [containerd](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/containerd/entry). First separate the developer-platform features from the runtime-daemon features. containerd can replace a lower runtime role without automatically replacing Docker build, Compose, networking, volume, and user-experience workflows.
- **When:** A platform uses Docker for image authoring while production Kubernetes nodes use containerd for execution. **Consider:** [Containers](https://github.com/BLCCoreStudio/OpenDevIndex/tree/concept/containers/entry), [Docker](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/docker/entry), [containerd](https://github.com/BLCCoreStudio/OpenDevIndex/tree/tool/containerd/entry). OCI image and runtime standards allow those layers to compose, while the container systems model explains why an image built through Docker can run through a different node runtime stack.
- **When:** Security review is treating a container as equivalent to a virtual machine boundary. **Consider:** [Containers](https://github.com/BLCCoreStudio/OpenDevIndex/tree/concept/containers/entry). Containers normally share the host kernel, so the correct threat model must include kernel attack surface, privilege configuration, namespaces, capabilities, seccomp, LSM policy, mounts, and host hardening.

## Notes

- This comparison intentionally mixes one foundational concept with two concrete tools because the main source of confusion is the abstraction boundary between them, not product feature parity.
- Docker, containerd, runc, OCI specifications, Kubernetes CRI, and CNI can compose in different ways across platforms and versions; verify concrete runtime stacks rather than assuming one universal layering diagram.
- Tool internals and defaults evolve, but the distinction between container systems primitives, a developer-facing platform, and a node-level runtime service remains a useful architecture model.
