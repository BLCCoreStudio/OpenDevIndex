# OpenTelemetry vs Prometheus vs Grafana

A role- and data-flow-first comparison of three observability technologies that often work together, clarifying which layer owns instrumentation, collection, metrics storage and query, visualization, and alert interaction.

**Verified:** 2026-09-06

## Compared modules

- [OpenTelemetry](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/opentelemetry/entry) (`cloud/opentelemetry`) — `deep-dive` — Vendor-neutral observability project defining APIs, SDKs, semantic conventions, and protocols for producing and transporting traces, metrics, and logs.
- [Prometheus](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/prometheus/entry) (`cloud/prometheus`) — `deep-dive` — Open-source monitoring and alerting system built around time-series metrics, label-based queries, pull-oriented scraping, and rule evaluation.
- [Grafana](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/grafana/entry) (`cloud/grafana`) — `deep-dive` — Observability visualization platform used to query, explore, dashboard, and alert on metrics, logs, traces, and other operational data sources.

## Comparison

| Dimension | [OpenTelemetry](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/opentelemetry/entry) | [Prometheus](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/prometheus/entry) | [Grafana](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/grafana/entry) |
| --- | --- | --- | --- |
| **Primary role** | Vendor-neutral telemetry framework and specification for instrumentation, context propagation, signal generation, collection, processing, and export across traces, metrics, logs, and evolving signals. | Metrics monitoring and alerting platform centered on labeled time series, pull-oriented scraping, local TSDB storage, PromQL, recording rules, and alert-rule evaluation. | Observability interaction and visualization platform that connects to external data sources, runs their query languages, transforms results, renders dashboards and Explore views, and manages alerting workflows. |
| **Application instrumentation** | A core responsibility. APIs, SDKs, automatic instrumentation, semantic conventions, Resources, Instrumentation Scope, and propagation provide a vendor-neutral way to produce correlated telemetry. | Supports metrics instrumentation through Prometheus client-library and exposition conventions, but it is not a general cross-signal instrumentation framework for traces, logs, and context propagation. | Usually consumes telemetry already available through configured data sources. It is not the primary application instrumentation API or SDK layer. |
| **Collection and processing pipeline** | The Collector provides receiver, processor, exporter, connector, and extension pipelines for routing, transforming, batching, sampling, filtering, and exporting telemetry to one or more backends. | Discovers targets and scrapes metrics directly, applies relabeling, stores local time series, and can federate or remote-write data. It is specialized around the Prometheus metrics model rather than a general telemetry pipeline. | Queries configured data sources and can transform query results for presentation. It does not normally replace a telemetry collection pipeline such as the OpenTelemetry Collector or Prometheus scraping layer. |
| **Native telemetry storage** | The specification and Collector are not a durable observability database. Telemetry is normally exported to backends that provide long-term storage, indexing, query, and retention policy. | Includes a local time-series database and WAL for metrics. Long-term, globally distributed, or very large retention architectures commonly add remote storage or compatible systems around Prometheus. | Generally queries external observability databases and APIs rather than acting as the primary durable store for metrics, traces, or logs. Its own application database holds Grafana configuration and state, not the monitored telemetry corpus. |
| **Metrics query language** | Defines telemetry data models and transport semantics but does not provide a universal backend query language comparable to PromQL. Query behavior belongs to the selected observability backend. | PromQL is a central capability for selecting, aggregating, transforming, and reasoning over labeled time series stored or exposed through Prometheus-compatible query APIs. | Uses the query language of each configured data source. With Prometheus it commonly sends PromQL through the Prometheus data-source integration rather than inventing a replacement metrics language. |
| **Distributed traces** | First-class trace instrumentation, context propagation, span processing, sampling, and OTLP export are core parts of the model. | Core Prometheus is a metrics system, not a distributed trace storage and query backend. Trace correlation can be connected through exemplars and external tracing systems. | Can visualize and explore traces when connected to a tracing data source, but the trace records are normally produced and stored elsewhere. |
| **Logs** | Defines log signal concepts and collection/export pipelines so logs can share Resource, context, and semantic-convention concepts with other telemetry. | Core Prometheus does not provide general log ingestion and storage; its primary data model is metrics time series. | Can query and visualize logs through log-capable data sources, but Grafana itself is normally not the durable log store. |
| **Dashboards and exploration** | Does not define a primary human dashboard or exploratory analysis UI. Its responsibility is getting well-described telemetry from producers through interoperable pipelines to analysis backends. | Provides metrics query and basic operational interfaces, but rich cross-team dashboard composition is commonly delegated to visualization systems such as Grafana. | Dashboards, panels, variables, transformations, Explore workflows, and cross-data-source visualization are central product responsibilities. |
| **Alerting responsibility** | Can transport and process telemetry that later drives alerts, but it is not itself the canonical end-user alert-rule and notification-management system for all backends. | Evaluates Prometheus alerting rules over metrics and sends alert instances into downstream notification handling, commonly through Alertmanager or compatible integrations. | Provides Grafana Alerting for evaluating supported data-source queries and expressions and for routing notifications, silences, contact points, and alert-management workflows. |
| **Protocol and interoperability boundary** | OTLP, semantic conventions, context propagation, signal data models, and Collector components are designed explicitly to reduce instrumentation and pipeline coupling to one observability vendor. | Prometheus exposition, scraping, HTTP query APIs, remote write, and its metrics data model form a widely integrated metrics interoperability boundary. | Integrates through data-source plugins and backend APIs. Its interoperability strength is presenting and correlating data from many systems rather than defining one telemetry transport protocol. |
| **Main scaling pressure** | Collector throughput, queueing, backpressure, retry behavior, sampling cost, processor complexity, exporter health, and telemetry volume determine pipeline capacity and loss risk. | Series cardinality, scrape volume, ingestion rate, query cost, retention, WAL and TSDB I/O, rule evaluation, remote-write queues, and HA topology dominate capacity planning. | Dashboard fan-out, expensive backend queries, concurrent users, alert-evaluation load, plugin behavior, metadata/database availability, and data-source latency dominate interactive performance and HA design. |
| **Typical failure boundary** | A failed or overloaded collector/export path can delay or drop telemetry even while the application remains healthy, so queues, retries, memory limits, and pipeline observability matter. | Scrape failures, cardinality explosions, disk pressure, slow queries, rule overload, remote-write backlog, or TSDB/WAL problems can reduce metrics visibility or alert reliability. | Data-source outages, query failures, dashboard mistakes, alerting configuration, plugin issues, or Grafana service/database failures can impair the operator view even while source telemetry still exists elsewhere. |
| **Choose or add when** | You need portable instrumentation, trace context, multi-signal telemetry pipelines, collector-side processing, or the ability to export the same application telemetry toward different backends. | You need pull-oriented metrics collection, a strong labeled time-series model, PromQL, local metric storage, recording rules, and metrics-driven alert evaluation. | You need human-facing dashboards, ad hoc exploration, multi-data-source views, visual correlation, presentation-layer transformations, and centralized alert interaction or notification workflows. |
| **Do not assume** | Do not assume OpenTelemetry replaces a durable metrics, trace, or log backend or a dashboard UI. It standardizes instrumentation and telemetry movement more than long-term analysis storage. | Do not assume Prometheus replaces a general multi-signal instrumentation standard or a full cross-backend visualization layer. Its strongest native boundary is metrics monitoring and alerting. | Do not assume Grafana replaces the telemetry producer, collector, or durable observability backend. A dashboard can disappear while the underlying Prometheus or other source data remains intact. |

## Decision guide

- **When:** The application must emit correlated traces, metrics, and logs without hard-coding one backend vendor throughout the codebase. **Consider:** [OpenTelemetry](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/opentelemetry/entry). OpenTelemetry provides the cross-signal APIs, SDKs, propagation, semantic conventions, OTLP, and Collector pipeline boundary designed for portable telemetry generation and export.
- **When:** The primary requirement is labeled infrastructure or application metrics with scraping, PromQL, recording rules, local TSDB behavior, and metric alert evaluation. **Consider:** [Prometheus](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/prometheus/entry). Prometheus owns that metrics lifecycle directly rather than acting only as an instrumentation transport or visualization client.
- **When:** Operators need dashboards and exploratory views across Prometheus and other observability backends from one interaction layer. **Consider:** [Grafana](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/grafana/entry). Grafana is designed to query external data sources and present their results through dashboards, Explore, transformations, and alerting interfaces.
- **When:** The goal is an end-to-end open observability path from application instrumentation through metrics storage to operator dashboards. **Consider:** [OpenTelemetry](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/opentelemetry/entry), [Prometheus](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/prometheus/entry), [Grafana](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/grafana/entry). A common architecture can use OpenTelemetry for instrumentation and pipeline processing, Prometheus for metrics collection or storage and PromQL, and Grafana for visualization and operator interaction; the exact integration path remains workload-specific.
- **When:** A team is replacing Prometheus with OpenTelemetry because both mention metrics. **Consider:** [OpenTelemetry](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/opentelemetry/entry), [Prometheus](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/prometheus/entry). Compare responsibilities before migrating. OpenTelemetry can generate and move metrics while Prometheus supplies a metrics database, scraper, PromQL engine, rules, and operational semantics that are not automatically replaced by an SDK or Collector.
- **When:** A team is replacing its telemetry backend with Grafana because dashboards already show the data. **Consider:** [Grafana](https://github.com/BLCCoreStudio/OpenDevIndex/tree/cloud/grafana/entry). Verify the actual data-source boundary first. Grafana commonly queries telemetry stored in another system, so the visible dashboard layer and the durable source of truth are different operational components.

## Notes

- These technologies frequently complement one another; this comparison is primarily about ownership boundaries and composition, not selecting a universal winner.
- Exact supported signals, Collector components, Prometheus interoperability paths, Grafana data-source capabilities, and alerting behavior are version-sensitive and should be checked against the linked deep dives before production changes.
- A real observability architecture may use only one or two of these technologies or combine them with other storage and analysis backends; the comparison does not prescribe a mandatory stack.
